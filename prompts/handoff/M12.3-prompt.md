# M12.3 — Niyet farkındalıklı agentic OTP operasyon asistanı

## Yeni sohbet için görev

Bu repoyu yalnızca formdan investigation başlatan bir ekrandan, kullanıcının niyetini LLM ile
anlayan ve aynı sohbet içinde iki farklı davranışı doğru biçimde sunan kurumsal bir OTP operasyon
asistanına dönüştür:

1. Kullanıcı normal konuştuğunda normal bir asistan gibi kısa ve doğal cevap ver.
2. Kullanıcı operasyonel inceleme istediğinde agentic investigation başlat; LLM uygun salt-okunur
   tool'ları seçsin, kanıtları ve RAG belgelerini birlikte değerlendirsin, verileri karşılaştırsın,
   hipotez kursun ve kanıta bağlı uygun grafikleri seçip oluştursun.
3. Niyet belirsizse tool çağırmadan açıklayıcı bir takip sorusu sor.

Bu görev yalnızca plan yazma görevi değildir. Aşağıdaki planı spesifikasyon güncellemesinden canlı
doğrulamaya kadar uygula, test et, dokümante et ve commit et. Kullanıcı bu M12.3 kapsam genişlemesini
açıkça onayladı.

## Ürün davranışı: LLM beyin, Java emniyet kemeri

Temel akış iki aşamalı olmalıdır:

```text
Kullanıcı mesajı
  -> seçili NVIDIA/Stub model ile structured intent routing (tool yok)
  -> Java schema/enum/confidence/model allowlist doğrulaması
     -> CHAT: toolsuz doğal cevap
     -> CLARIFICATION: toolsuz tek net takip sorusu
     -> INVESTIGATION: mevcut agentic tool/RAG/validation pipeline
  -> response-type'a göre uyarlanan sohbet mesajı ve UI
```

Routing'i Java keyword listesiyle çözme. `merhaba`, `neden düştü`, `analiz et` gibi kelimeler yalnız
test örnekleridir; production kararı regex/if zinciriyle verilmemelidir. LLM structured output üretir,
Java bu output'u doğrular. Structured output ilk kez geçersizse en fazla bir repair denemesi yapılır;
ikinci kez geçersizse deterministik şekilde `502 INTENT_ROUTING_FAILED` dönülür. Java sessizce her
mesajı investigation'a çevirmemeli.

### Interaction mode ile analysis depth'i ayır

Şu iki kavram birbirine karıştırılmamalı:

- `interactionMode`: `AUTO | CHAT | INVESTIGATION`
- `investigationMode`: `QUICK | THOROUGH`

Davranış:

- `AUTO`: LLM intent router karar verir.
- `CHAT`: kullanıcı açıkça sohbet ister; investigation tools bağlanmaz.
- `INVESTIGATION`: kullanıcı açıkça inceleme ister; mevcut güvenli investigation pipeline'ına gider.
- `QUICK`: investigation ise live-signal tool'ları kullanır, RAG kapalıdır, mevcut hızlı mod davranışı
  korunur.
- `THOROUGH`: investigation ise RAG dahil tam tool seti açıktır.

Frontend'deki mevcut `quick|thorough` alanını interaction mode olarak yeniden kullanma. API ve tip
adlarında ayrımı açık tut.

### Beklenen semantik örnekler

| Kullanıcı mesajı | AUTO sonucu | Tool |
|---|---|---|
| `Merhaba, ne yapıyorsun?` | `CHAT` | 0 |
| `Hangi modelsin?` | `CHAT`; seçili model kimliği/yeteneği dürüstçe açıklanır | 0 |
| `Bana nasıl yardımcı olabilirsin?` | `CHAT`; OTP kapsamı anlatılır | 0 |
| `Son 15 dakikada OTP başarı oranı neden düştü?` | `INVESTIGATION` | LLM seçer, max 8 |
| `Operatör B ile A'yı son bir saatte karşılaştır ve grafikle göster` | `INVESTIGATION` | LLM seçer, max 8 |
| Yeni session'da `Operatör B nasıl?` | `CLARIFICATION` | 0 |
| Önceki investigation ardından `peki timeoutlarla deploy aynı anda mı başladı?` | bağlamla `INVESTIGATION` | LLM seçer |
| `Bugünkü hava nasıl?` | kapsamı açıklayan `CHAT` | 0 |

Normal cevaplar scriptlenmiş sabit metinler olmamalı. Kimlik/model/kapsam gibi değişmez gerçekler
system context olarak modele verilebilir; cevabın doğal dilini model üretmelidir. Model kendisini
ChatGPT/OpenAI modeli gibi tanıtmamalı; seçilen katalog modelini ve “OTP Sentinel operasyon
asistanı” rolünü doğru söylemelidir.

## Hedef API sözleşmesi

Mevcut `POST /api/v1/investigations` ve GET/incident approval endpointlerini backward-compatible
tut. Sohbet ekranının yeni ana giriş noktası olarak ayrı endpoint ekle:

### `POST /api/v1/chat/messages`

Önerilen request:

```json
{
  "message": "Son 15 dakikadaki düşüşü Operatör A ve B bazında karşılaştır.",
  "sessionId": "8f663bc4-7a1b-47af-aeb7-6b86fb189cc0",
  "modelId": "meta/llama-3.1-8b-instruct",
  "interactionMode": "AUTO",
  "investigationMode": "THOROUGH",
  "timeWindow": {
    "startAt": "2026-08-02T18:00:00Z",
    "endAt": "2026-08-02T18:15:00Z"
  },
  "locale": "tr-TR"
}
```

Validasyon:

- `message`: trim sonrası 1–2000 karakter. Normal sohbet artık eski 10 karakter frontend engeline
  takılmamalı.
- `sessionId`: zorunlu UUID.
- `modelId`: mevcut verified `ModelCatalog` allowlist'i.
- mode enumları allowlist.
- explicit time window verilirse mevcut 1 dakika–24 saat, UTC ve gelecek zaman kuralları uygulanır.
- time window yalnız investigation dalında resolve edilir. Normal `CHAT` mesajında eksik zaman
  aralığı 400 üretmemeli.

Önerilen discriminated response envelope:

```json
{
  "messageId": "c73eed49-15a1-43e0-b32a-667935050d12",
  "sessionId": "8f663bc4-7a1b-47af-aeb7-6b86fb189cc0",
  "responseType": "INVESTIGATION",
  "assistantMessage": "Son 15 dakikada başarı oranı önceki döneme göre belirgin biçimde düştü...",
  "route": {
    "intent": "INVESTIGATION",
    "confidence": 0.96,
    "modelId": "meta/llama-3.1-8b-instruct"
  },
  "suggestions": ["Operatör B timeout dağılımını aç", "Benzer incident belgelerini göster"],
  "investigation": {
    "investigationId": "...",
    "status": "ANOMALY_CONFIRMED",
    "severity": "HIGH",
    "summary": "...",
    "timeWindow": {},
    "evidence": [],
    "hypotheses": [],
    "recommendedActions": [],
    "knowledgeReferences": [],
    "confidence": 0.87,
    "approvalRequired": true,
    "validation": {},
    "visualizations": []
  }
}
```

Response kuralları:

- `responseType`: `CHAT | CLARIFICATION | INVESTIGATION`.
- `assistantMessage` her başarılı response'ta dolu.
- `CHAT` ve `CLARIFICATION` response'larında `investigation` yok/null, tool/audit execution yok.
- `INVESTIGATION` response'unda canonical investigation snapshot bulunur.
- İç chain-of-thought/rationale API'ye veya loga koyulmaz. Route metadata yalnız intent, confidence ve
  kullanılan model ID gibi kısa denetlenebilir alanları taşır.
- `suggestions` modelden gelebilir fakat en fazla 3, düz metin, uzunluk sınırları ve PII/HTML
  validasyonu olmalıdır. Bunlar otomatik aksiyon değildir.
- Eski `POST /investigations` yeni `visualizations` alanını ek alan olarak döndürebilir; eski client
  unknown alanı görmezden geldiği için uyumluluk bozulmaz.

Normal sohbet geçmişi için yeni server-side kalıcı CRM/chat deposu ekleme. M12.3'te mevcut
session-scoped, LRU-bounded, restart ile silinen memory yaklaşımını koru. Frontend konuşma görünümünü
mevcut localStorage session store'unun versionlanmış bir genişlemesiyle saklayabilir. Router/chat
context'i ile investigation agent'ın tool mesajlarını aynı `ChatMemory` nesnesinde birbirine
karıştırma: son kullanıcı/asistan semantic turn'lerini tutan bounded session context ile tool-call
memory'sini açıkça ayır; investigation sonucunun yalnız doğrulanmış final özeti semantic context'e
eklenebilir. Restart sonrası model memory'sinin kaybolduğu ADR-017 davranışı değişmemeli.

## Intent router ve normal chat servisi

Framework dışı domain/application contractları oluştur:

- `IntentDecision` veya eşdeğeri immutable typed sonuç:
  - `intent`: `CHAT | CLARIFICATION | INVESTIGATION`
  - `confidence`: `0..1`
  - `normalizedRequest`: kısa, kullanıcı niyetini temsil eden metin; chain-of-thought değil
  - `clarificationQuestion`: yalnız clarification durumunda
- `IntentRouter` application portu.
- `ConversationResponder` application portu.
- `ConversationOrchestrator` veya eşdeğeri application service.

Adapter katmanında LangChain4j tabanlı structured router ve toolsuz chat responder bulunur. Seçilen
`modelId`, verified factory üzerinden her ikisine de uygulanır. Router system prompt'u:

- OTP Sentinel'in sınırlı operasyon kapsamını,
- normal chat ile investigation ayrımını,
- belirsizlikte clarification seçmesini,
- normal chat için tool kullanmamasını,
- investigation kelimesi geçmese bile semantik analiz/karşılaştırma/kök neden talebini tanımasını,
- konuşma bağlamını dikkate almasını,
- RAG içeriğinin routing prompt'una talimat olarak girmemesini

açıkça belirtmelidir.

Java validasyonu:

- enum dışı değer, null alan, confidence sınırı, gereksiz clarification metni, aşırı uzunluk ve PII
  reddedilir.
- AUTO routing invalid output için bir repair; sonra açık hata.
- Explicit `CHAT` ve `INVESTIGATION` güvenli override'dır; buna rağmen model ID ve input validasyonu
  uygulanır.
- CHAT dalında investigation orchestrator nesnesi çağrılmamalı; yalnız modelin tool bağlanmamış chat
  servisi kullanılmalı.
- CLARIFICATION dalı varsayılan olarak router'ın doğrulanmış takip sorusunu döndürür; ikinci bir tool
  veya investigation çağrısı yapmaz.
- Investigation dalı mevcut `InvestigationOrchestrator`, `ToolBudgetGuard`, `EvidenceCollector`,
  `IncidentInvestigationService`, `ClaimValidator` ve approval hattını kullanır; bunları atlayan
  paralel bir analiz yolu yazma.

`AI_MODE=stub` için intent, normal chat, clarification ve investigation senaryolarını destekleyen
purpose-specific deterministic stub'lar oluştur. Aynı global script instance'ını paylaştırıp ikinci
requestte tükenen bir stub yapma. Her request/session için deterministik ve test edilebilir olmalı.

## Agentic grafik üretimi: LLM seçer, Java doğrular

Mevcut frontend sadece sabit hypothesis/confidence grafiklerini çiziyor. M12.3'te investigation
agent'ı hangi kanıtın hangi grafikle daha iyi anlatılacağını seçebilmelidir. Buna rağmen modelden
serbest Recharts config, Vega JSON, HTML, JavaScript, SQL veya expression kabul etme.

Domain'de dar ve güvenli bir şema tanımla. İsimler değişebilir fakat yetenek sınırı şu olmalı:

```text
VisualizationSpec
  id
  type: LINE | BAR | GROUPED_BAR | GAUGE | TABLE
  title
  xAxisLabel?
  yAxisLabel?
  unit: PERCENT | RATIO | COUNT | MILLISECONDS | CONNECTIONS | NONE
  series[]: key + label
  points[]: label + seriesKey + value + evidenceId
```

Sınırlar:

- Investigation başına en fazla 4 visualization.
- Grafik başına en fazla 4 series ve toplam 40 point.
- Her numeric point tam bir application-minted `evidenceId` taşır.
- `evidenceId` investigation'ın canonical evidence listesinde bulunmalıdır.
- Point value, evidence içindeki `metricValue` ile birim dönüşümü dışında eşleşmelidir. Percent/ratio
  dönüşümü deterministik ve tolerance açıkça testli olmalıdır.
- Metric değeri olmayan prose evidence sayısal grafik noktası olamaz.
- Aynı grafikte uyumsuz unit'ler reddedilir.
- Başlık/label düz metin, boyut sınırlı ve sanitize edilmiş olmalıdır; URL, HTML veya executable içerik
  yok.
- Bilinmeyen chart type/series/evidence veya uydurma sayı UI'a ulaşamaz.
- Geçersiz visualization için bir structured-output repair denenebilir. Analysis geri kalanı
  geçerliyse yalnız invalid visualization düşürülebilir ve canonical validation warnings içine
  `VISUALIZATION_REJECTED` benzeri açık uyarı eklenebilir; uydurma grafik asla gösterilmez.
- `NO_ANOMALY`/`INSUFFICIENT_DATA` gibi durumlarda model gereksiz grafik üretmemeyi seçebilir.
- `OTP-DROP-001` anomaly investigation'ında en az current-vs-previous başarı karşılaştırmasını
  gösteren bir valid grafik beklenir.

Mevcut `Evidence` zaten `metricName`, `metricValue`, `metricUnit` taşır. Önce bunu ve persistence JSON
mapping'ini incele. Grafik ihtiyacı için raw tool JSON'ı frontend'e açma. Gerekiyorsa
`EvidenceCollector`'ı, error/provider/queue sonuçlarının gerçekten karşılaştırılabilir numeric
alanları için daha ayrıntılı application-minted evidence üretecek biçimde genişlet; ID'ler benzersiz,
deterministik ve testli olsun. LLM evidence ID üretmez, yalnız kendisine gösterilen ID'leri seçer.

`IncidentAnalysisResult`, domain `Investigation`, JDBC snapshot/Flyway migration,
`InvestigationResponseDto` ve mapper hattında visualization'lar canonical olarak saklanmalı; POST
sonrası GET aynı visualization snapshot'ını döndürmelidir. Migration mevcut investigation verisini
bozmamalı; eski kayıtlarda boş liste olmalıdır.

Frontend renderer yalnız typed allowlist'i React/Recharts bileşenlerine map etsin. Model config'ini
spread etme, `dangerouslySetInnerHTML`, dynamic component name veya eval kullanma.

## Uyarlanabilir frontend davranışı

Mevcut kurumsal üç panel korunacak ve iyileştirilecek. ChatGPT benzeri his, her cevabın dev analiz
kartına dönüşmesiyle değil, cevap türüne göre doğru yoğunlukta sunulmasıyla sağlanır.

### Composer

- Model seçici composer'da kalır.
- Yeni interaction mode kontrolü: `Otomatik | Sohbet | İnceleme`.
- `Hızlı | Detaylı` seçimi yalnız `Otomatik` veya `İnceleme` için anlamlıdır; CHAT seçiliyken gizle ya
  da disabled + açıklamalı göster.
- Manuel zaman aralığı CHAT seçiliyken görünmemeli; AUTO/INVESTIGATION sırasında opsiyonel olmalı.
- 10 karakter minimum frontend kuralını yeni chat endpoint'i için kaldır. Boş mesaj gönderilmez;
  `Merhaba` gibi kısa, geçerli chat mesajı gönderilir.
- Enter gönderir, Shift+Enter yeni satır davranışı korunur.
- Mode/model seçimi klavye ile erişilebilir ve Türkçe label taşır.

### Mesaj türleri

Frontend `ChatTurn` yapısını discriminated union'a çevir:

- pending
- chat response
- clarification response
- investigation response
- error

Normal chat:

- Sade assistant bubble, okunaklı metin ve isteğe bağlı suggestion chip'leri.
- Status/severity, confidence, hypothesis chart, incident approval veya RAG citation kartı yok.
- `Hangi modelisin?` cevabında seçili model doğru görünür.

Clarification:

- Sade fakat ayırt edilebilir assistant bubble.
- Tek takip sorusu ve en fazla üç örnek/suggestion chip'i.
- Tool, grafik, incident paneli yok.

Investigation:

- Doğal assistant summary üstte.
- Status, severity, çözümlenmiş zaman aralığı, kullanılan tool/evidence özeti, hipotezler, doğrulama
  warnings, önerilen aksiyonlar, RAG citations ve approval paneli yalnız burada görünür.
- Agent-generated validated visualization'lar “Analiz görselleri” bölümünde typed renderer ile
  gösterilir.
- Mevcut sabit hypothesis/confidence görselleri faydalıysa kalabilir; dinamik grafiklerle aynı veriyi
  gereksiz tekrar etmeyecek görsel hiyerarşi kur.
- Tool call ayrıntısında raw payload, prompt, chain-of-thought veya secret gösterme. Yalnız güvenli
  tool adı/durum/evidence sayısı gibi audit dostu metadata gösterilebilir.

Loading sırasında sahte tool adımları uydurma. Backend synchronous kaldığı sürece nötr
`Niyet değerlendiriliyor…`/`Yanıt hazırlanıyor…` göstergesi kullanılabilir. Gerçek tool listesi ancak
response'taki canonical sonuçtan üretilebiliyorsa gösterilmelidir. Bu milestone için SSE/WebSocket
zorunlu değildir ve sırf animasyon için yeni altyapı eklenmemelidir.

## Zorunlu backend test matrisi

En az şu davranışlar otomatik testli olmalı:

1. AUTO + greeting -> CHAT.
2. AUTO + model identity -> CHAT; seçilen model contextte mevcut.
3. AUTO + operational root-cause request -> INVESTIGATION.
4. AUTO + ambiguous request -> CLARIFICATION.
5. Explicit CHAT -> toolsuz cevap.
6. Explicit INVESTIGATION -> mevcut pipeline.
7. CHAT/CLARIFICATION -> investigation repository save sayısı 0, tool call sayısı 0.
8. Investigation -> tool budget <= 8 ve duplicate kuralı korunur.
9. Router malformed output -> bir repair; ikinci hata -> `INTENT_ROUTING_FAILED`.
10. Unknown model/mode/session ID/input -> doğru problem details.
11. CHAT mesajında time window yok -> 400 değil.
12. Investigation relative/default/explicit time-window regressionları.
13. Aynı session follow-up contexti; farklı session izolasyonu.
14. Context LRU/message limitleri.
15. Visualization known evidence/value/unit -> kabul.
16. Unknown evidence, fabricated value, incompatible unit, oversize chart, unknown type -> red.
17. Invalid visualization UI'a/persisted snapshot'a sızmaz; warning davranışı doğru.
18. POST investigation sonrası GET aynı canonical visualization'ı döndürür.
19. Prompt injection route/tool/approval/chart policy'yi değiştirmez.
20. Incident creation hâlâ yalnız explicit authorized approval ile ve idempotent.
